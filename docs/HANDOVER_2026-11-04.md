`+2.37519e-9`, 순간가열은 거의0이어서 net process 사이의 상쇄는 거의 없다. 그럼에도
gross line 흐름 `9.83050`으로 나눈 잔차는 `3.37e-7`이고 channel-normalized 값은
`0.99835`다. gross 기준 수용치가 매우 작은 절대 잔차를 뜻할 수는 있지만, 독립 BB
항들이 열평형을 서로 상쇄했다는 뜻은 아니다.

같은 저장값의 미보정 BB 순열은 node36에서 `-1.35680e-5`여서 SCL_LN 적용 뒤 부호가
바뀐다. 90점 중 36점에서 미보정/보정 BB 순열 부호가 다르고 최대 보정 차이는 node90의
`5.59100e-2`다. node89/90의 보정 BB 순열은 각각 `-4.84596e-3`/`-4.83182e-3`이고,
동일점의 순간가열 `+4.58963e-3`/`+4.59731e-3`와 거의 상쇄되어 전체 잔차는
`-3.01e-8`/`-1.27e-7`이다. 따라서 SCL_LN 연결은 열장부의 핵심 민감항이다. 이 값은
CMFGEN 제어와 기존 구현을 재대조한 것이며, line-resolved `LINEHEAT`/`NETRATE` 부재로
현재 입력에서 보정된 BB 성분의 native parity는 아직 미검증이다. 부호 차이만으로
구현 오류나 새 회귀라고 판정하지 않는다.

`1ae7732da87b3eef017143f38a46ac23f920100bfd9490b33cd790076c8a2348`,

job `1264295` 제출 전까지 재사용 가능했던 같은 상태의 CMFGEN 보존본에는

래퍼가 필수 활성화 환경변수
`LUMINA_FIXEDJ_HEAT_ONLY=1`을 전달하지 않아 `STOP94`로 실패했고, 필요한 출력은
생성되지 않았다. 이후 동일 입력·자원 범위의 교정 단회 재제출을 승인받아 전용 실행기를
추가하고, 해시·제어·산출물 사전/사후 확인을 직접 시험했다(관련 57개 시험 통과).
새 격리 출력으로 제출한 job `1264261`은 3초 만에 batch exit2로 실패했다. Slurm이
스크립트를 spool 위치에 복사해 실행하는데 실행기가 `BASH_SOURCE[0]`에서 저장소 위치를
추정해 Python 파일을 찾지 못했다. `srun`과 CMFGEN은 시작하지 않았고 물리 출력은 없다.
이 launcher 오류를 고쳐 spool 경로를 흉내 낸 통합시험과 관련 57개 시험을 통과했다.
그때까지 승인된 교정 1회는 이후 job `1264295` 제출에 사용됐다. 새 staging과 실패
로그는 보존한다. 과거 유사 출력의 추가 저장량 추정은 약4.75 GiB다.

그 뒤 실제 자기일관성을 닫으려면 같은 수용 물질로 새 J를 계산하고 물질응답을 다시
구해야 한다. 새 transport는 Syntax GPU Slurm에서 실행할 단계지만, `1262975` 계약은
새 transport 0회였고 이 후속 수송도 현재 승인되지 않았다. 최종 스펙트럼·물리량 비교,
Si II/III·S 이온화 동질성 및 공동수렴은 모두 **미달/미입증 (`NOT_MET`)**이다.

## 선택 물질의 native 고정상태 입력 검증

완료 result SHA256 `be3bf940802800c7df94396e1fbd6a8828aa444a9c444082582179349f1eaf47`을
입력으로 `prepare_lumina_accepted_material.py`를 실행해 evaluation4의 마지막 실제 수용
상태만 별도 export했다. source kind는 `FINITE_NEW_FIELD_TNE_ACCEPTED_STEP`; 90점,
1,798개 SL/terminal 열과 24,542개 full level이다. 후보의 전하 상대오차 최대
`2.20e-15`, 핵종수 상대오차 최대 `1.49e-15`, 정상 SE 잔차 최대 `1.03e-16`이다.
저장 occupation 복원은 정확 일치, full-level 재구성 상대오차 최대 `8.64e-16`이다.
이 export는 새 BF/BB 적분·SE·수송을 수행하지 않는다.

이 물질을 native 고정상태 입력 `NATIVE_HEAT_INPUT.bin`으로 직렬화했다. 파일 크기는
1,296,752 byte, SHA256은
`a5603029f30c7fa2335e6efcf6dbb6c86e973e7bf3fcf6d7a17f28e1f73c09c4`이며 manifest SHA256은
`13c150bfea860f160eb3a4593e601936759b5fbe2e330bc935cf68fd6c98cf47`이다. 별도 readback에서
native 입력 1,800행(1,798 population + ne + T), 90개 반경점, 반경/T/ne 및 모든 population
행이 exporter의 예상 배열과 정확히 일치했다(최대 절대차 `0`). 이는 현재 선택 상태의
native 입력 배선·직렬화 증거이지 CMFGEN이 이 상태를 실제 평가했다는 증거는 아니다.

state-only manifest에는 `radiation_input=NOT_PREPARED`, `actual_native_evaluation=false`,
`heat_policy=NOT_YET_MATCHED`로 기록돼 있다. 이후 같은 F-1 J를 native EDD 입력으로
직렬화했다. `fixedj-field-input.json` SHA256은
`4e768b008fbc00c256d64fc88bc07bf59148e24dbc8f3840fb9441f1569672d2`이며 입력 J SHA256은
`40a48d9aedaafa4d8f6f8adb0fdb6ea191bd152ed3f55de38e8862fe445232a6`다. 생성된
`EDDFACTOR` SHA256 `47f78fb98810704e9b0dcf4f664e8e2a38170e5d2b68d644879fb6b447b5692d`는
이전 fixed-J 포획에서 확인한 같은 J의 native EDD와 일치하고, `EDDFACTOR_INFO` SHA256은
`2c032445a9483d5154c15cdac5c0f14dfbb3f45dbb628e2d4936c29b3efabd42`다. 90점·1,115,020
주파수 값을 보존했으며 native quadrature가 Lumina 격자와 같다고 주장하지 않는다.

job `1264295` 제출 직전에는 수용 T/ne·population 입력과 고정 J 입력이 준비됐지만,
유효한 native `LINEHEAT`/`NETRATE` 포획은 아직 0회였다. 첫 Grammar 제출
`1264146`은 CPU16·32GiB·최대4시간·GPU0·재시도0이었으나 21초 뒤 실패했다. Slurm step은
`94:0`, batch는 `31:0`이며 네 필수 출력은 생성되지 않았다. 동일 범위로 승인된 교정
제출 `1264261`은 CPU16·32GiB 할당 3초 뒤 batch `2:0`으로 실패했으며 Slurm step과
CMFGEN 실행은 없었다. 이 두 시도는 native line/heat output을 만들지 못했다. 이후
승인된 `1264295` 포획 결과와 별도 비교는 문서 첫 절에 기록했다. 새 수송·최종 물질
수용은 여전히 0회다.

원인은 제출 래퍼가 실행파일의 필수 활성화 환경변수
`LUMINA_FIXEDJ_HEAT_ONLY=1`을 전달하지 않아 `cmfgen_fixedj_heat.f90`의 fail-closed
가드가 `STOP 94`를 낸 것이다. 물리 입력/해시 오류나 다른 프로젝트의 취소가 원인은
아니다. 두 실패의 staging·로그는 보존했다. 전용 실행기는 배치와 `srun` 양쪽에서
활성화 변수를 지정하고, sealed 입력 해시와 `WRITE_RATES=T`를 확인한다. Slurm이 배치
스크립트를 spool 위치에서 실행한다는 점을 반영해 저장소 루트를 명시 인자로 전달하도록
고쳤으며, spool 모의 통합시험과 관련 57개 시험이 통과했다. 그러나 교정 단회 승인은
이미 사용했으므로 추가 제출에는 새 승인이 필요하다. 새 자기일관 수송은 이후 Syntax GPU
Slurm 단계지만 별도 승인 전에는 시작하지 않는다.

같은 날 계정의 Grammar·Syntax Slurm 회계에서 11월1일 이후 Lumina/CMFGEN 작업을
대조했다. 해당 범위에는 `CANCELLED` 기록이 없었다. Grammar의 관련 과거 작업은
완료 또는 별도 원인의 실패이며, Syntax에는 현재 실행 중인 Lumina/CMFGEN 작업이 없고
과거 `444706`, `447806`은 이미 기록된 DNS 실패다. 따라서 타 프로젝트 취소로 사라진
기존 관련 작업은 확인되지 않았다. `1264146`은 별개의 래퍼 설정 오류로 실패했으며,
그 교정 제출 `1264261`도 저장소 루트 탐색 오류로 srun 전 실패했다. 이는 타 프로젝트
취소와 무관하며, 추가 제출은 새 승인 대기다.

## fixed-J 실행파일 신원 대조 정정

기존 fixed-J 실행파일 SHA `a51c7e5c90b94b7d6e56cd586b426c73b2f3813d9096f894f0f4f776072812d9`를
보존 build들과 대조했다. 이전 인계에서 source `0d494…`와 `84e3…`를 서로 다른 upstream
판본으로 해석한 것은 부정확했다. 실제 job manifest는 input source `84e3…`, 패치 생성된
`cmfgen_sub.f` output `0d494…`, 실행파일 `a51c…`를 기록하며, 동일한 세 값이 보존된
Lageunha build manifest에서도 일치한다. 즉 `0d494…`는 fixed-J observer 패치 결과이고
`84e3…`는 패치 전 입력이다. 기존 실행파일/원본 자료는 수정하지 않았다. 이 신원 정정은
실행 권한을 새로 부여하지 않는다. `WRITE_RATES=T` capture의 첫 승인 실행은 job
`1264146`에서 래퍼 환경변수 누락으로 실패했다. 사용자가 동일 범위의 교정 단회를 승인해
`1264261`을 제출했으나, Slurm spool 위치에서 저장소 루트를 잘못 추정해 srun 전에
실패했다. 같은 단회 승인 범위의 재시도는 소진됐고 추가 제출은 새 승인 대기다.
