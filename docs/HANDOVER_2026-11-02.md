## 후속 실행시간 정정 — 새 복사장에서는 열 방향 응답 재계산 필요

앞의 21:44 기록에 적힌 직렬 약10시간07분은 다음 새 복사장에서 필요한 새
온도·전하 방향 응답 네 개를 빠뜨린 과소 추정이다. `1254013`은 이전 J에 대한
네 섭동을 실제 계산해 4시간20분28초(CPU16·32GiB) 걸렸다. 재생 코드
`lumina_thermal_replay.load()`는 보존 방향의 `field` 신원이 현재 field와
정확히 같아야만 재사용을 허용한다. 따라서 새 transport가 새 J를 만들면 이전
J의 네 응답을 넘겨 쓰지 않고 다시 계산해야 한다.

한 번의 새 물질→계수/경계→F→물질응답→새 J 방향 네 응답→T/ne 수정 묶음의
실측 유사 단계 합은 다음과 같다: 계수생성 `1250253` 29분46초, H200 F worker
`444706` 4시간54분44초, 새-J 물질응답 `1253439` 2시간22분02초, 새 방향 응답
`1254013` 4시간20분28초, T/ne 수정 `1257134` 2시간20분45초. 합계는 약
**14시간27분45초의 계산시간**이며 Slurm 대기시간은 별도다. `444706` 자체는
worker가 전 주파수를 처리한 뒤 dispatcher DNS 문제로 FAILED였으므로, 이 단계
시간은 유사 worker 처리량이지 성공한 새 bundle의 완주 보장은 아니다. 다른 GPU
세대·새 입력의 처리량도 보장하지 않는다.

이 시간은 한 outer iteration만의 추정이다. 반복 수렴 횟수, 유효한 matched-physics
steady CMFGEN 기준해, 최종 observer spectrum 비교는 포함하지 않는다. 이에 따라
기존 10:07 추정은 실행예산으로 사용하지 않는다. 새 수송이나 재계산은 현재 승인
범위를 벗어나므로 제출하지 않았다.

## 후속 실행 보호 — GPU 노드의 Grammar callback 사전 접속

이전 주소 보존 수정은 DNS 이름 대신 명시 IP와 기존 SSH alias/엄격한 host-key를
사용하게 했지만, 제출 준비에서 IP 형식이 유효하다는 것만으로 실제 Syntax 계산
노드의 연결 성공까지 보장하지는 않았다. 과거 F worker처럼 전 주파수 계산 후
callback에서 실패하는 일을 줄이기 위해, 묶음 제어 구성이 있을 때
`submit_lumina_accepted_feedback.slurm`이 F worker보다 먼저 실제 계산 노드에서
`grammar` 접속과 host-key 검증을 1회 확인하도록 보강했다. 이 확인은 SSH alias,
수치 주소, strict host-key를 그대로 사용하며 timeout 15초·재시도0회다.
실패하면 같은 할당에서 장시간 수송을 시작하지 않는다.

`pytest -q tests/test_lumina_bundle_dispatch.py`: 48 passed. 합성 묶음시험은
호출 순서가 preflight→F→반환장 제출이며 preflight 실패 시 F가 시작되지 않음을
확인했다. 실제 계산 노드 연결은 아직 시험하지 않았고, 승인된 새 수송도 제출하지
않았다. 따라서 이는 이전 DNS 실패의 낭비 경로를 fail-fast로 막은 코드 수정이지,
다음 원격 callback의 실제 성공 증거나 물리 결과가 아니다. 새-J outer iteration
승인은 아직 대기 중이고 최종 물리 목표는 **NOT_MET**다.
